# 把「黑塔」的设置收进 DSH —— 第二轮：删掉她的设置页

> 状态：**已实施**（2026-09-26）。上一轮（同日早些时候）只做了「DSH 里单开一页
> 黑塔、把值写回她读的文件」；这一轮是**收口**：她的设置页整块删除、写回整块删除、
> 密钥与两个真动作补进 DSH、字段表逐项标注「整机到底读不读它」。
>
> 本文记的是**实际落地的东西**。设计底稿在根目录 `_herta-settings-統合設計.md`，
> 两份说的是同一件事，避免各说一套。

## 1. 这一轮改了什么（一句话版）

**DSH 设置 ▸ 黑塔是黑塔全部设置的唯一入口。** 她的整机界面里那套设置面板
（`SettingsModal` + 7 个分页 + 侧栏那个齿轮按钮）已经不存在；插件也不再往
她自己的 `settings.json` 写任何一个字节。

```
DSH 设置 ▸ 黑塔
  ├─ 界面       界面语言 / 主题
  ├─ 语音       引擎（+ 试听）/ 实时语音 / 静音 / 音量 / MiniMax 状态（认领·回落·上限）
  ├─ 差分协处理器  3D 设备卡
  ├─ 密钥       MiMo 密钥 / MiniMax 密钥 / MiniMax 套餐密钥   ← 走 DSH 凭据存储
  ├─ 整机动作    本地语音模型（下载·取消·删除） / 安装包网盘
  └─ 暂未接线    9 项，逐行标注「谁该读它、现在缺什么」
```

## 2. 数据流（唯一真相）

```
DSH 设置页（settings.section ▸ 黑塔）
  │  ctx.configForms.get("herta").set(field, value)
  ▼
profile 的 cordis.patch.yml 里那条 herta 条目        ← 唯一真相（明文）
  │  loader 提交进 volatile 引用（不重挂插件）
  ▼
客户端快照 machineValues()
  ├─► DSH 设置页的控件
  └─► 整机 iframe 的 postMessage 应答器（getLocale / getTheme / getVoicePrefs …）

密钥走另一条：
DSH 设置页 ▸ 黑塔 ▸ 密钥
  │  ctx.remote.credentials.set(ref, value)
  ▼
$DSH_HOME/.credentials.yaml（0600，file 层）
```

**没有写回了。** 上一轮还有第三条箭头：宿主侧 `settings-sync.js` 把用户覆盖过的
字段写回 `%APPDATA%\Herta\settings.json` 与 `<workspace>\.herta\settings.json`。
它已整体删除，理由见 §4。

## 3. 字段表：逐项说明「整机到底读不读它」

`src/host/settings-schema.js` 的 `FIELDS` 仍然是唯一一处字段清单；页面标签、枚举
选项、默认值、以及 `wired` 注解**全部从它生成**。没有第二份清单。

| 凭据 ref | 消费者 |

**2026-09-27 更新**：MiniMax 那两个密钥**已经有消费方了** —— 助手正文会经宿主分段后
送去云端合成，再经 SSE 推给界面播放（边写边念、可被复核否决掐掉、每轮 800 字上限）。
云端不可用（没密钥 / 没认领到克隆 / 被拒绝 / 克隆被 MiniMax 删掉）时**显式回落本地

会上传参考音频现克隆一个），所以那份 8.36 MB 的 `herta-reference.wav` 不需要进插件。
认领靠 tag `b1a43133` —— 它正好是那份 wav 的 SHA-256 前 8 位，也是上游为兼容旧克隆
留的常量。

### 3.3 真动作（有宿主实现，按下去有后果）

| 动作 | 宿主实现 |
|---|---|
| 本地语音模型 下载 / 取消 / 删除 | `voice-model-route.js` + `voice-model.js`，装到 `$DSH_HOME/tts/`；进度靠轮询 |
| 打开网盘 | `NETDISK_URL`（`shared/links.ts` 的同一串）在新标签页打开 |

**没有搬的两个动作**，以及为什么：

- **检查更新 / 重启并安装** —— 那是 `electron-updater` 在 **Electron 主进程**里做的
  事，只有独立安装的 `Herta.exe` 有。iframe 里没有主进程，DSH 也不负责更新整机。
  搬过去只能做成按不动的控件，所以随设置页一起删掉。
- **克隆重试**（`prepareMiniMaxVoice`）—— 现在**仍然没有**这个动作，但理由变了：
  本插件只认领、不克隆，所以没有"重试克隆"这回事。要重新认领，用设置页那颗
  「重新认领」按钮（`POST /herta-minimax-state {"action":"adopt"}`）。

### 3.4 「暂未接线」的 9 项

`interactionLanguage`、`closeToTray`、`autoUpdate`、
`workspace`、`dreamEnabled`、`backendThinking`、`backendContract`、`modelsActor`、
`modelsBackend`。

（原来是 11 项，2026-09-27 移出两项：`voiceEngine` —— 宿主现在按它分发，
`minimax` 走云端合成、云端不可用则显式回落本地模型；`realtimeVoice` —— 它是
**自动念回复**的总开关，关掉就不再自动送去合成，而 `herta_say` 不受它管。
`local` / `mimo` 两条本轮刻意不动。）

比「干净」重要；为什么不假装它们能用：`wired: false` + `note` 就是不留假象的

### 3.5 2026-09-28：两个"已接线但没行"的字段终于出现在页面上

`voiceEngine` / `realtimeVoice` 在 09-27 被移出这一组（因为它们真的接线了），
但**没有任何人把它们加进正式分组** —— 而页面的渲染只遍历
「`SETTINGS_GROUPS` 的各组」与「`UNWIRED_FIELD_NAMES`」两处。两处名单各说各的，
合起来就是：这两个字段在设置页上**一行都不渲染**，改引擎只能手改 profile 的
`cordis.patch.yml`。

这一轮把它收掉，并且**让这类漏配以后能被断言抓住**：

- 分组表搬到 `src/host/settings-groups.js`（纯数据、无 import）。客户端 import 它
  （esbuild 内联），`scripts/test-herta-settings.mjs` 也 import 它 —— 于是"字段进了
  分组"这件事有了单测：**每个 `WIRED_FIELD_NAMES` 必须落在某个分组里**。
- 「语音」组的顺序改成：引擎 → 实时语音 → 静音 → 音量 → 状态行（`MiniMaxVoiceRow`
  从组首挪到组尾：先选，再看后果）。
- `local` 那一档从「只在云端失败时被**回落**调用」变成**直选就会念**：判据从
  两处字面量 `!== "minimax"` 收成一处 `speaksFor()`（`local` / `minimax` 会出声，
  `mimo` 不会）。`mimo` 留在取值域里、并在行下写明"尚未接线"，是决定不是遗漏。
- 新增「试听」按钮：台词（用户定的「有事吗？没事我就走了」）由**宿主**持有，
  界面只发 `POST /herta-minimax-state {action:"preview"}`；PCM 仍走那条 SSE。
  静音时按钮旁提示并给一键取消静音 —— 试听走浏览器播放路径，那条路有静音闸门。

代价曾如实记下（2026-09-28 早些时候）：`local` 每次合成都起一个子进程、重载 85 MB
模型，实测约 3 秒/句 —— 这一条当时也写进了设置页。

**同一天晚些时候它被修掉了**：那 3 秒被量出来**全是模型加载**（2.6–3.7 s），推理
只有音频时长的 0.28 倍。于是本地合成改走**常驻进程**（加载一次 + 空闲 10 分钟回收 +
切到「本地模型」时预热），设置页多了一行「合成进程：已预热 / 启动中… / 未启动」。
真机实测：**冷 4.2 s → 热 1.01 s**，试听台词热 1.00 s。设计与数字记在
[本地合成常驻化.md](./本地合成常驻化.md)。

为什么 `workspace` 也在这一组：这个字段的全部用途就是给上一版的写回指路
（「写回哪个工作区」），写回删了，它就只剩被存下来。

## 4. 删掉的东西，以及为什么

| 删掉的 | 理由 |
|---|---|
| `Herta-src` 的 `components/Settings/` 里 22 个文件（`SettingsModal` + 7 分页 + `SettingRow`/`Toggle` + 各自单测） | 用户要求「删除黑塔整机的设置页」。`Select.tsx` **保留** —— 它不是设置页独占的，`FileViewer/renderers/LogView.tsx` 也在用（见 §6.2） |
| `App.tsx` 的 `SettingsModal` 渲染与 `settingsOpen` | 同上 |
| `Sidebar.tsx` 的 `.sidebar-settings` 按钮与 `onOpenSettings` prop；`icons.tsx` 的 `SettingsIcon` | 它是弹层的唯一入口 |
| `src/host/settings-sync.js`（整份）+ `lib/settings-sync.js` | 见下 |
| 首次种子迁移 `readHeretaSeed` | 它把整机文件里的值搬进 Config。文件不再被读了，搬进来只是把死值固化 |
| `followedFields` 字段 + 客户的「↺ 跟随整机」复位 | 它是**种子的出口**：没有种子，就没有「跟随」可言 |
| 旧语音偏好文件的一次性迁移（`dsh-herta-voice.json` → `.imported`） | 与写回同属一条链路。它只在 0.1.2/0.1.3 那一版需要，且迁移早已在真机跑过 |
| 宿主里的 `settingsSnapshot` / `isVolatileRef` / `VOLATILE_WRITE` | 只为写回而存在 |

### 4.1 为什么写回可以整块删（两条实测事实）

1. **嵌在 DSH 里的整机从来不读那些文件。** 它的每一个设置都经 postMessage 向父窗口
   要，父窗口再读 `ctx.configForms.get("herta")`（`src/client/index.tsx` 的应答器）。
   也就是说「唯一真相只有一份」在上一轮就已经成立了。写回是在给一个**没有读者**
   的文件做维护。
2. **读那两份文件的是独立安装的 `Herta.exe`**，而用户已判定它不再维护。

顺带删掉的还有那三条不变量里的两条（「只写用户覆盖过的字段」「只并写我们管的键」）
—— 它们保护的是**她的文件**，而那个文件已经不在这条链路上。

## 5. 一个必须记住的连带事实：她的设置页是那些 getter 唯一的消费者

删页之前逐个查过「谁还在读这个 bridge getter」，结果并不整齐：

| bridge getter | 删页后还有谁调 |
|---|---|
| `getLocale` | `App.tsx` 启动（**活**） |
| `getTheme` | `lib/theme.ts`（**活**） |
| `getDeviceScene` | `device-scene-prefs.ts`（**活**） |
| `getVoicePrefs`（本轮新增） | `voice-prefs.ts` → 播放路径（**活**） |
| `getDreamConfig` / `getCloseToTray` / `getAutoUpdate` / `getInteractionLanguage` / `getBackendConfig` / `getModelConfig` / `getRealtimeVoice` / `getVoiceEngine` | **没人了** —— 它们此前只被她那些设置分页调用 |

后八个的应答器**仍然留在** `src/client/index.tsx` 里，理由写在那段注释里：
`HertaBridge` 契约把这些成员声明为**必填**（`bridge-types.ts:617-672`），少一个就是
类型错，而那是上游文件；而且它们正是「暂未接线」那组字段将来的落点。
**「有分支」不等于「有人调」** —— 事实记在字段表的 `wired` / `note` 上。

## 6. 两个踩到的坑（都写进注释了）

### 6.1 「哪些组件是设置页独占的」不能靠印象

第一次核查用的模式是 `components/Settings/<name>` 与 `from "./<name>.js"`，于是漏掉了
`LogView.tsx` 里的 `from "../../Settings/Select.js"`。`Select` 被当独占组件删掉之后，
构建才会失败。修法：从另一份克隆 `Herta-github` 里恢复 `Select.tsx` + 它的单测，并在
`scripts/test-herta-settings.mjs` 里加一条**断言它必须存在**（带原因），免得下一个人
再删一次。

教训：删一个目录之前，要按「任何形式的引用」搜一遍，而不是按你预期的写法搜。

### 6.2 死 CSS 与死 i18n 留着

`reference-ux.css` 里 `.settings-nav` / `.settings-backdrop` / `.sidebar-settings` 这批
规则、以及 i18n 里 `nav.group.*` 等键，在她那边已经没有组件渲染了。它们**留着**：
CSS 是上游大文件，删规则的风险（误伤共享类名）大于收益；而 `.settings-backdrop`
仍被保留的 `KeyPrompt` 使用。
验证时不要因为 bundle 里还能 grep 到这些字符串就以为组件还在 —— 客户端 bundle
内联了整份 `reference-ux.css`，那些命中来自样式文本。

### 6.3 凭据缝必须用 `ctx.get` 取，不能用 `inject`（真机三次构建才试出来）

密钥要写进 DSH 的凭据缝，而拿这个服务的三种写法里只有一种能用：

| 写法 | 结果 |
|---|---|
| `ctx.inject(["remote.credentials"], cb)` | **回调不触发**。三行密钥全显示「凭据服务不可用」 |
| `ctx.inject(["remote"], cb)` 后读 `scoped.remote.credentials` | 不可靠：第一次构建里回调触发了（那次没读属性），之后两次连回调都没来、计时器也没到超时——与「读属性抛异常」一致 |
| `ctx.get("remote.credentials")` | **第一次尝试就拿到**（诊断标记 `settingsCredentialsAttempts = 1`） |

原因大概是：`credentials` 是 **handshake 之后挂到 `remote` 对象上的命名空间**，
不是 cordis 能等的独立服务路径。所以最终实现是
`resolveCredentials()`（两种取法都包在 try 里）+ `watchCredentials()`（500 ms × 40 次
的有界轮询，随 fiber 释放），并给每一次结果都留诊断标记。

**这里最值得记的不是结论，是中间那次误判**：第一个版本把 `remote` 本身当成凭据对象，
`inject(["remote"])` 成功了、标记写成 `settingsCredentialsBound: true`，而每一次
`describe` 都失败 —— 页面全线「不可用」，标记却在说「已绑定」。所以现在有两个标记：
`settingsCredentialsBound`（注入/解析成功）与 `credentialsStatusError`（**调用**失败）。
**一个标记只能证明它测的那件事**；把它当成「功能可用」是最容易骗过自己的一步。

另外，凭据缝可能是握手之后才出现的，而密钥行在挂载时就会查一次状态 ——
所以还有一张订阅表（`subscribeCredentials`），服务到了会让那几行自动重查，
否则界面会永久停在「不可用」，即使服务半秒后就绪。
